# 조사 에이전트 — 2026-10-13

원자료: `reports/investigate_eval.json` (최종, 프롬프트 v3) · `reports/investigate_eval_prompt_v2.json` · `reports/investigate_prompt_v1_partial.json`
코드: `src/wafer/investigate.py` · `scripts/investigate.py` · `scripts/investigate_eval.py` · `tests/test_investigate.py`

기존 판독 에이전트(고정 순서 파이프라인)는 건드리지 않고 도구를 호출하는 에이전트를 따로 추가했다. 같은 웨이퍼로 두 방식을 견주었다. 정답이 있는 집합 중 아는 패턴 96장은 파이프라인이 더 정확했다. 학습에서 뺀 패턴 24장은 에이전트의 사람 확인 비율이 높았지만 그 차이의 일부는 판단이 아니라 루프가 중간에 끊긴 몫이다. 깨진 맵은 파이프라인에 맞는 route 가 없어 같은 기준으로 견줄 수 없다.

## 도구와 submit 검사

도구 5개는 모두 결정적 코드다. LLM 이 정하는 것은 어떤 도구를 몇 번, 어떤 순서로 부를지, route 와 카드 문장이다.

| 도구 | 반환 |
|---|---|
| `look(row)` | 상위 3개 패턴 확률 · 처음 보는 패턴 백분위와 경고(파이프라인과 같은 임베딩 kNN 점수) · 웨이퍼 면적과 `quality_ok`(면적 < 0.5 이면 false) |
| `locate(row)` | `locate.describe` 결과 |
| `similar(row, pool, k)` | 임베딩이 가까운 웨이퍼 k개(번호 · 라벨 · 로트 · 거리). pool 은 라벨 있는 학습 웨이퍼 표본 또는 라벨 없는 웨이퍼 6만 장 표본 |
| `lot_neighbors(row)` | 같은 로트와 번호가 ±3 이내이면서 다이 크기가 같은 웨이퍼 중 이 웨이퍼와 가까운 수, 가까운 것들의 예측 패턴, 가장 가까운 3장 |
| `causes(pattern)` | `causes.json` 의 원인 후보 |
| `submit(card)` | 아래 검사를 통과하면 ok, 아니면 문제 목록 |

`lot_neighbors` 의 가깝다는 기준: 라벨이 다른 학습 웨이퍼 쌍 20만 개의 코사인 거리 하위 5 %. 모델마다 임베딩 공간이 달라 모델별로 잰다. `lot_s0` 는 0.2844 이고 이 값보다 가까운 쌍이 같은 불량 패턴 쌍의 88.5 % 다. 학습에서 한 종류를 뺀 모델 8개는 기준이 0.2178~0.3097, 같은 패턴 쌍 비율이 71.8~92.8 % 였다.

submit 의 코드 검사
- evidence 의 `{tool, key, value}` 는 이 세션에서 그 도구가 실제로 돌려준 값과 같아야 한다(key 는 결과 JSON 을 점 경로로 편 이름).
- 판정: look 1위와 같은 패턴, 처음 보는 패턴 경고 꺼짐.
- 맵 이상: look 이 quality_ok=false 를 보여 준 경우.
- 새 패턴 후보: 경고 켜짐, evidence 에 lot_neighbors 항목 1개 이상.
- cause_ids 는 판정일 때만. 기존 `check()` 는 판정이면 아는 패턴 카드 규칙으로, 그 밖의 route 는 원인 없음 · 고정 점검 문장 규칙으로 적용한다.
- 한도: 도구 8회를 넘기면 route "사람 확인", reason "조사 한도 초과". 실제 평가 160장 중에는 한도에 걸린 적이 없다(최대 7회). 한도 동작은 테스트로만 확인했다.

## 평가 집합

- (a) `reports/agent_eval.json` 의 120장: 아는 패턴 96장(`lot_s0`) + 학습에서 한 종류를 뺀 모델에 그 종류를 준 24장.
- (b) 라벨 없는 웨이퍼 중 면적 < 0.5 인 2,628장에서 20장(시드 2). 프롬프트 v2 평가에서는 시드 1 표본을 썼고 두 표본은 겹치지 않는다.
- (c) 맵 품질 검사를 통과한 라벨 없는 웨이퍼 중 `runs/unlabeled_novelty.npy` 점수가 가장 높은 20장. 정답이 없다.

(a) 의 웨이퍼 번호는 `agent_eval.json` 에 저장된 것을 그대로 썼다. 같은 시드로 다시 뽑아 보니 그 번호가 나오지 않았다(저장된 실행과 지금 코드의 난수 소비 순서가 다르다). 그래서 Reader 의 kNN 참조 표본이 원래 실행과 다르고, 처음 보는 패턴 경고가 저장된 값과 같은 웨이퍼는 120장 중 117장(97.5 %)이다.

파이프라인 쪽 (a) 수치는 `agent_eval.json` 을 재사용했고, (b)(c) 는 같은 코드(`read_card`)로 이번에 돌렸다. 파이프라인에는 맵 이상 route 가 없다. 경고가 켜지면 "처음 보는 패턴", 꺼지면 판정으로 본다.

- v2 와 v3 를 돌릴 때 코드의 `evidence.key` 처리에 버그가 있었다. 대괄호 표기를 점 경로로 바꾸려다 숫자가 지워져 `hits..label` 이 되었고, 결과적으로 대괄호 표기는 거절됐다. 수정하려던 코드를 되돌려 평가한 코드와 저장소 코드를 같게 했다(대괄호 표기는 계속 거절된다).

## 혼합 모드

조사 에이전트는 어려운 웨이퍼에만 쓰고 나머지는 파이프라인이 판정으로 처리하는 구성이다. `scripts/investigate.py --hybrid` 로 한 장씩, `scripts/investigate_eval.py --hybrid-only` 로 평가를 계산한다. 원자료는 `reports/investigate_hybrid_eval.json`.

배정 규칙: 아래 중 하나라도 해당하면 에이전트, 아니면 파이프라인이 판정(패턴은 look 1위)으로 처리한다.
- 처음 보는 패턴 경고 켜짐
- 맵 품질 이상(quality_ok=false)
- 1위 확률 < 0.7

파이프라인에는 낮은 확신 규칙이 없다. 그래서 기준값을 따로 정했다. 0.7 은 혼합 모드를 계산하기 전에, 에이전트 프롬프트의 안내값(`LOW_CONF`)으로 이미 쓰고 있던 숫자다. 그 값은 `agent_eval.json` 의 아는 패턴 96장에서 분류기 확신도별 정답률을 보고 골랐다: 확신도 0.7 미만 14장은 정답률 43 %, 이상 82장은 98.8 %. 같은 96장에서 고른 값이라 이 집합에 한해서는 표본 안 선택이다. 혼합 모드 결과를 보고 바꾸지 않았고, 다른 값은 시험하지 않았다.

LLM 은 다시 돌리지 않았다. 에이전트로 간 웨이퍼는 `investigate_eval.json` 의 v3 기록을, 파이프라인으로 간 웨이퍼는 (a) 는 `agent_eval.json` 의 시간을, (b)(c) 는 이번에 돌린 파이프라인 시간을 쓴다. 필요한 기록이 빠진 경우는 없었다. 파이프라인 쪽 판정 패턴은 look 1위(= 분류기 예측)이고, 저장된 파이프라인 경고가 look 과 다른 3장은 look 을 기준으로 배정했다.

- (a) 뺀 패턴: 에이전트만과 같은 19 / 24. 파이프라인으로 간 4장은 모두 확률 0.7 이상 · 경고 꺼짐이어서 판정으로 나갔고 틀렸다.
- 이번 결과는 한 번 돌린 기록에서 계산한 것이고, 기준값이 (a) 아는 패턴 96장에서 정해졌다는 점 때문에 그 집합의 81.3 % 는 낙관적일 수 있다.

## 읽기

- 정답이 있는 (a) 에서 아는 패턴 판정은 파이프라인이 낫다(86.5 % 대 66.7 %). 경고가 꺼진 88장 중 65장만 판정으로 끝났고, 나머지 23장 중 16장은 루프가 끝나지 못했다(도구 호출 없이 끝남 · 제출 3회 거절). 7장은 LLM 이 1위 확률이 0.7 미만이라고 사람 확인을 골랐다.
- 학습에서 뺀 패턴 24장의 판정 아님 비율은 79.2 % 로 파이프라인(62.5 %)보다 높다. 경고가 켜진 14장은 모두 새 패턴 후보 13 · 사람 확인 1 로 갔고(경고 규칙은 파이프라인과 같다, 파이프라인은 15장), 경고가 꺼진 10장 중 5장이 사람 확인(LLM 이 고른 4장 · 루프 실패 1장)으로 갔다. 경고가 꺼진 나머지 5장은 판정으로 나갔고 모두 틀렸다.
- 깨진 맵(b) 은 면적 한 줄이면 걸러지는 문제이고 코드 규칙이 파이프라인 앞에 있었다면 20장 모두 잡았을 것이다. 에이전트가 맵 이상으로 보낸 것은 16장이고, 나머지 4장은 새 패턴 후보 3 · 사람 확인(도구 호출 없이 끝남) 1 이다.
- (c) 20장은 정답이 없어 맞고 틀림을 말하지 않는다. 확인할 수 있는 것은 에이전트가 이웃 로트 조회를 근거로 인용했다는 점이고, 이웃 로트에서 같은 모양이 반복된다는 주장은 13장에서만 근거(n_close > 0)가 있다.

## 실패 예시

- 판정 오류 1건: 행 776092(정답 Loc)는 look 1위가 Scratch 0.959 · 경고 꺼짐이어서 판정 Scratch 로 통과했다. 분류기 오류는 도구로 고칠 수 없다.
- 학습에서 뺀 패턴이 판정으로 나간 5건: 행 763708(뺀 패턴 Loc)은 look 1위 Center 0.864, 이상 점수 백분위 91.4, 경고 꺼짐이다. 경고가 꺼지면 에이전트도 판정을 낼 수 있고 파이프라인도 같은 웨이퍼를 놓쳤다.
- 글로만 답하고 끝남(행 361616, 정답 Edge-Loc): `locate` 와 `causes` 를 부른 뒤 "이제 submit 를 호출하여 카드를 제출하겠습니다. route 판정 …" 이라고 카드를 글로 쓰고 호출하지 않았다. 재촉 2번에도 같은 응답이어서 사람 확인으로 끝났다.
- 고칠 내용만 글로 쓰고 끝남(행 679658): submit 이 check_order 개수로 거절된 뒤 "2개 이상을 추가하겠습니다"라고 쓰고 다시 호출하지 않았다.
- 값 오류(행 369469): `lot_neighbors.close_pred.none = 'none'` 이라고 적었다. 도구가 돌려준 값은 58 이었다. key 의 이름과 값을 혼동했다.
- 이웃이 없는 근거(행 244135): 새 패턴 후보로 통과했지만 인용한 lot_neighbors 의 `n_close` 는 0 이었다. 규칙은 항목의 존재만 요구한다.
- 깨진 맵인데 새 패턴 후보(행 344812 · 352551 · 429664, 면적 0.278~0.307): v3 에서도 남은 3장이다.

## 한계

- 표본이 작고 시드 1회다. (a) 아는 패턴 96장은 v2 와 v3 사이 7점 흔들렸다. 표 안의 백분율은 신뢰구간 없이 읽어야 한다.
- 4B 모델은 submit 형식을 자주 틀린다(첫 제출 통과 27.6 %). 코드 검사가 이를 걸러내므로 통과한 카드는 규칙을 지키지만, 걸러내는 과정에서 17장은 도구 호출 없이 끝났고 5장은 제출을 3번 거절당했다.
- 코드 검사는 근거가 도구 결과와 같은지만 본다. 근거가 주장을 뒷받침하는지(예: n_close 가 0 인데 반복된다고 쓰는 것)는 보지 않는다. 판정에서 깨진 맵을 막는 규칙도 없다(설계에 없었다). 이번 (b) 에서는 판정이 0장이었다.
- 사람 확인 route 의 `reason` 은 프롬프트가 쓰라고 하지만 코드가 강제하지 않는다. 제출 검사를 통과한 사람 확인 카드 11장(전체 160장 중)은 모두 reason 이 비어 있었다.
- 분류 모델과 kNN 참조 표본이 원래 `agent_eval.json` 실행과 달라 (a) 의 파이프라인 숫자와 에이전트 숫자는 경고 3장에서 다른 Reader 를 본다.
- 초 단위는 공유 Ollama 의 대기 때문에 부풀었다.
- (c) 는 정답이 없다. 새 패턴 후보라는 route 가 실제 새 패턴을 뜻하는지는 사람이 봐야 한다.
